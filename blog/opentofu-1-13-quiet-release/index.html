OpenTofu 1.13: the quiet release that fixes my loudest plans

The release notes call it "relatively light". For anyone who has stared at a wall of (known after apply), it's a good one.

OpenTofu 1.13.0 came out at the end of September 2026. The latest patch at the time of writing is 1.13.8, published yesterday, and it fixes a regression in the -v flag. The maintainers were upfront that the cycle was short and the feature list is modest. I almost skipped it.

But my working week is mostly Terragrunt stacks, plans that run through a CI pipeline, and reviewing other people's diffs. For that kind of work, the small changes in 1.12 and 1.13 make a real difference. This post covers the ones I'm actually adopting, plus the upgrade notes that will catch someone out.

Plans you can actually read

Every infrastructure engineer knows the feeling. You change one tag, and the plan shows forty lines of (known after apply) spreading through every module that touches the value. Reviewers can't tell a harmless change from a dangerous one, so they approve anyway. That's where incidents come from.

1.13 adds two tools for this. The first is convert. It takes a value whose shape OpenTofu can't infer, such as the output of jsondecode() on something only known after apply, and gives it an explicit type. The plan can then reason about the structure even while the contents are unknown:

output "example" {
  value = convert(
    jsondecode(something_dynamic.example.output_json),
    object({ id = string, tags = map(string) })
  )
}

The second is the assume… family. With these functions you tell the planner something you know about a value it hasn't seen yet, for example "this will never be null" or "this VPC ID will start with vpc-":

output "vpc_id" {
  value = assumenotnull(assumestringprefix(aws_vpc.example.id, "vpc-"))
}

There's a catch, and the maintainers say it plainly: if your assumption turns out to be wrong, the apply fails. I see that as a feature. It's like a type annotation for infrastructure. It documents what you expect and fails loudly when you're wrong, instead of quietly creating the wrong thing.

Guard rails that change per environment

This one is from 1.12 (May 2026), but it's the change I've been waiting longest for. prevent_destroy can now refer to input variables in the same module. It used to be a hard-coded literal, which left you two bad options. You could protect the database everywhere and fight the guard every time you tore down a sandbox. Or you could protect it nowhere and hope.

variable "prevent_destroy_database" {
  type    = bool
  default = true
}

resource "example_database" "example" {
  lifecycle {
    prevent_destroy = var.prevent_destroy_database
  }
}

I look after a sandbox environment that is destroyed and rebuilt on a schedule, so this matters to me. The safe default stays in the module, and the one environment that needs to be disposable says so explicitly, in a line a reviewer will notice.

1.12 also added lifecycle { destroy = false }. It lets you remove an object from state without destroying the real resource. That's useful when a resource moves to another stack or is handed to another team. Before, this meant running tofu state rm in a terminal, with no review and no record. Now it's a code change that goes through a PR like everything else.

Smaller things I noticed

  • -json-into=FILE (1.12). Machine-readable output goes to a file, and the normal human-readable output stays in the terminal. CI pipelines no longer have to choose between logs people can read and output tools can parse.
  • Linting, experimental (1.13). Basic linting is available through a -lint flag on supported commands. It's early, but a linter built into the tool could mean one less separate tool to keep pinned in CI.
  • Symbol Libraries, experimental (1.13). These are shared type definitions and user-defined functions written in HCL. The maintainers call the syntax "just a starting point", so I'm watching rather than adopting, but it targets real copy-paste pain across modules.
  • Saved plans include provider schemas, so tofu show on a plan file can often skip starting providers. Plan-review jobs get faster.
  • Windows on ARM64 is now an official platform.

Upgrade notes that will bite someone

Read these before you change the version pin in your CI image.
  • WinRM is gone. It was deprecated in 1.12, and a connection block with type = "winrm" is now an error. The remote-exec and file provisioners lost WinRM support.
  • base64gzip output changed. It's "equivalent but not byte-for-byte identical", so resources that store that output may show a diff. Plan before you apply, and use ignore_changes if you need to.
  • macOS 13 Ventura or later is now required.
  • Last release series for 32-bit builds. 1.13 is the last series with official 386 and arm builds, and 1.14 drops them. Check old self-hosted runners.
  • Stricter SSH parsing. Some invalid input that was accepted before is now rejected.

Where this leaves OpenTofu

Looking back over the last few releases, OpenTofu has steadily fixed long-standing annoyances. 1.10 brought OCI registry support for providers and modules, and native S3 state locking without DynamoDB. 1.11 added ephemeral resources and the enabled meta-argument. 1.12 made prevent_destroy dynamic. 1.13 cleaned up plans.

None of these are headline features. Each one is a workaround I can delete. As someone who reviews more plans than I write, that kind of release suits me.

My upgrade plan: move CI to 1.13.8, run plans across every stack and check for base64gzip diffs, then start adding assume… functions to the modules with the noisiest plans.
