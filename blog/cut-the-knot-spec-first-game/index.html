I built a mind game spec-first, and the harness did the arguing

A six-minute browser game, 37 numbered requirements, and a test suite that refuses to merge anything the spec doesn't mention. Here's how it fits together, and what it caught.

I recently read The Courage to Be Disliked by Ichiro Kishimi and Fumitake Koga. It's a dialogue about Alfred Adler's psychology: the idea that we act towards goals rather than being pushed by our past, that most friction comes from mixing up our tasks with other people's, and that life is lived in moments rather than on the way to a summit. I wanted to turn those ideas into something you do rather than read, and I wanted it on my CV site.

The result is Cut the Knot, a five-night game. The game itself is small. What I want to write about is how it was built. I treated a hobby project the way I'd like platform work to be treated: the spec comes first, every requirement is traced to a test, and the rules about structure are enforced by machines rather than by memory.

The game in brief

Each night turns one idea from the book into a mechanic. All the words are my own; the book is credited as inspiration.

  • Cause or Goal: pick the hidden goal behind an excuse. The card flips from "because…" to "so that…".
  • Fuel or Excuse: sort lines into healthy striving, an excuse, or a mask.
  • Whose Task?: swipe Mine or Theirs. It ends with a round you can only win by giving up on keeping ten people happy.
  • Level the Line: praise and blame tilt a line between you and someone else. Only thanks levels it.
  • Dance the Dots: catch the "now" dot while thoughts about the past and future drift by. There's deliberately no timer.

It's plain JavaScript: no framework, no build step, no package.json. GitHub Pages serves it as static files, and pushing to main deploys it.

Spec first, literally

The first commit contains no code. It's a SPEC.md with requirements like this:

- **REQ-N5-1** Night 5 shows one "now" dot at a time for a short life.
  It can be tapped or caught with Space / Enter. Thought bubbles labelled
  past or future drift in, and tapping one costs points. No countdown
  timer or progress bar is shown during play. That is the point.

The second commit adds tests that cite those IDs in their names, and all of them fail, because nothing exists yet. Only the third commit adds the game. The git history reads spec → red → green, so anyone reviewing it can see that the behaviour was decided before the implementation.

That last sentence of REQ-N5-1 matters more than it looks. An eager contributor, human or AI, will "helpfully" add a progress bar to a timed game. Writing down why it's absent, and having the end-to-end test fail if a timer appears, turns a design decision into something the build defends.

The harness

By harness I mean everything around the code that lets someone change it safely without holding the whole project in their head: the map, the constraints, and the feedback loops. Here it has four parts.

1. A map: AGENTS.md

A one-page file in the game folder says where everything is, which commands to run, which rules are enforced, and the gotchas (for example: bump the ?v= cache-buster when you change an asset, and don't "fix" the missing timer). It's written for a new contributor, and that includes an AI coding agent, which reads it before touching anything. If the map is wrong, fixing it is part of the change.

2. Traceability that fails the build

This is the core of the harness and it's tiny. One test reads every REQ-… ID from the spec and every ID cited in the tests, and fails if they don't match in either direction:

test("REQ-HARNESS-3 every requirement in SPEC.md is cited by a test", () => {
  const missing = [...specIds].filter((id) => !cited.has(id));
  assert.deepEqual(missing, [], `untested requirements: ${missing.join(", ")}`);
});

test("REQ-HARNESS-3 tests only cite requirements that exist in SPEC.md", () => {
  const unknown = [...cited].filter((id) => !specIds.has(id));
  assert.deepEqual(unknown, [], `unknown requirement ids: ${unknown.join(", ")}`);
});

Add a requirement and forget to test it: red. Delete a requirement but leave its test: red. The spec can't quietly drift from reality, which is the usual fate of a design doc.

3. Architecture rules as tests

The game has three layers: engine.js (pure logic: scoring, a seeded RNG, routing, saving progress through an injected storage adapter), content.js (only data), and ui.js (the only file allowed to touch the DOM). Rules like that usually live in a reviewer's head. Here they're a test:

test("REQ-ARCH-1 engine.js is pure: no DOM, window, storage globals or timers", () => {
  const src = code(read("src/engine.js"));
  for (const banned of ["document", "window", "localStorage", "setTimeout",
    "requestAnimationFrame", "Math.random"]) {
    assert.ok(!src.includes(banned), `engine.js must not use ${banned}`);
  }
});

Banning Math.random in the engine means every shuffle goes through a seeded generator, so a game can be replayed exactly from its seed. The same file also enforces a 150 KB budget (the game is about 75 KB), no third-party scripts, and zero npm dependencies. The content tests check a safety deny-list, phone-friendly text lengths, and an originality guard: no quotation longer than twelve words, and none of the book's character labels.

4. An end-to-end test with no dependencies

I didn't want Playwright or Puppeteer in a repo that has no package.json. Modern Node ships fetch and a global WebSocket, and that's all you need to talk to Chrome's DevTools Protocol directly:

const target = await (await fetch(`http://127.0.0.1:${port}/json/new?about:blank`,
  { method: "PUT" })).json();
const ws = new WebSocket(target.webSocketDebuggerUrl);
// ...then Runtime.evaluate to click through the game, and
// Runtime.exceptionThrown / Log.entryAdded to fail on any page error.

About 250 lines play all five nights to the finale with a ?test=1 flag that speeds up the timers. Along the way they check that the Night 1 card flips, that the approval round settles into the right split, that Night 5 shows no timer, that progress survives in localStorage, that deep links and the back button work, and that sharing falls back gracefully when the browser has no share API. GitHub's Ubuntu runners already have Chrome, so CI needs nothing extra. With --shots it also saves screenshots in light and dark mode at phone and desktop sizes, so a reviewer (or an agent) can actually see the change.

What the harness caught

  • A tooling gotcha on day one. On Node 23, node --test some/dir/ tried to run the directory as a single file. The spec, map and CI now all use the glob form "tests/*.test.mjs", and a test checks the CI workflow uses it.
  • A design bug found by playing. In the approval round, every face drained to zero within about two seconds. That felt hopeless rather than draining. The fix started in the spec ("drains steadily; each click restores +35"), then the test (a 4-clicks-a-second player must still lose ground, but slowly), and only then the engine.
  • A flaky teardown in CI. All nineteen end-to-end checks passed, then the job failed while deleting Chrome's profile folder, because Chrome was still writing to it. It now waits for Chrome to exit and retries the delete, and cleanup can't fail the run.

The numbers

  • 37 requirements, 43 fast tests (under a second), 19 end-to-end checks (about 5 seconds in CI)
  • About 75 KB of game files, no build step and no npm packages
  • One small later feature, an owner-only answer key on my private admin page, went through the same loop: new requirement, failing test, code, CI

Want to try it? Go and cut the knot. It takes about six minutes, and you sign in with Google so your progress follows you between devices.

And if any of these ideas land, please read The Courage to Be Disliked itself. The game only scratches the surface of a conversation that's well worth the full book.
