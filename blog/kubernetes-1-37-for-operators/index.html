Kubernetes v1.37, read from the operator's chair

Release posts list everything that changed. This one is about what changes for the people who run the clusters.

Kubernetes v1.37 "Garhwal" came out on 26 August 2026, with 67 enhancements. I didn't read the release post that week. I was busy upgrading a service mesh across three clusters, which taught me (again) that most upgrade problems are versions you lost track of, not new features.

So I've reread the release notes the way I read a change request: what will break, what has started a countdown, and what is good enough to use now. My clusters are still on 1.34, so v1.37 is three control-plane upgrades away. That distance makes the deprecations more important to me than the new features.

The clocks that started ticking

A deprecation doesn't break anything on the day it's announced. It sets a date for later. In this release cycle, four changes set dates that will matter to most operators:

  • kube-proxy ipvs mode is deprecated (KEP-5495). The project says that by v1.40 it is "expected to be disabled by default (still selectable via the feature gate)", and by v1.43 "support for ipvs mode would be removed entirely." Clusters now log a deprecation warning at startup. If you chose IPVS years ago for performance, plan a move to nftables mode.
  • kube-dns is deprecated. No new packages are expected after v1.40. Most clusters moved to CoreDNS long ago, but older self-managed ones may still run kube-dns.
  • Static Pods can no longer reference Secrets or ConfigMaps, and the PreventStaticPodAPIReferences gate that let you opt out has been removed. If an old bootstrap script relies on this, it breaks on v1.37.
  • cgroup v1 support is on its way out (KEP-5573). failCgroupV1 has defaulted to true since v1.35. Setting failCgroupV1: false still works as a temporary override in v1.37, but support "is planned to be removed in a future release."

Add the v1.36 changes you may have missed. The gitRepo volume plugin is now permanently disabled. Service .spec.externalIPs is deprecated, with removal planned for v1.43. Together, these give the timeline below.

The timeline makes one thing obvious. v1.43 removes both IPVS and externalIPs. If either is buried in an old Helm chart, you'll be glad to find it in 2026 rather than discover it at an upgrade gate in 2028.

How I'm finding the stragglers

The API server already tells you which deprecated APIs are still being called. I check this metric before every upgrade:

kubectl get --raw /metrics | grep apiserver_requested_deprecated_apis

Each line includes a removed_release label, so you can sort by urgency. For the kube-proxy mode, check the kube-proxy ConfigMap (or your managed add-on's configuration) on each cluster. For IPVS in particular, run that check now rather than at v1.40.

Life after Ingress NGINX

The biggest operational news of 2026 wasn't in a release at all. Ingress NGINX was retired on 24 March 2026. The original announcement was blunt: "there will be no further releases, no bugfixes, and no updates to resolve any security vulnerabilities that may be discovered." Existing installs keep working, which is exactly why it's easy to ignore.

The official advice from SIG Network and the Security Response Committee is to start migrating immediately, either to Gateway API (the recommended path) or to another Ingress controller. One line from their January statement stuck with me: "None of the available alternatives are direct drop-in replacements." That's been my experience too. The YAML is the easy part. The hard part is the annotations nobody wrote down and the regex rewrites someone added in 2021.

The first step is a one-liner from the retirement post. It's worth running against every cluster you own, including the "temporary" ones:

kubectl get pods --all-namespaces --selector app.kubernetes.io/name=ingress-nginx

Ingress2Gateway reached 1.0 in March and will turn most of your Ingress objects into Gateway API resources. Treat its output as a first draft, not a finished migration. The project's "Before You Migrate" post lists five ingress-nginx behaviours that will surprise you, and it's worth reading before the first route goes live.

What graduated that I'd actually use

Sixteen features went GA in v1.37. Most are niche, but these are the ones I'm excited about:

  • Pod Certificates (KEP-4317) and ClusterTrustBundles (KEP-3257). These are built-in ways to give Pods X.509 identities and distribute CA bundles. Not every workload needs a mesh or an extra controller just to get a certificate, and this is a big step towards that.
  • Configurable HPA tolerance (KEP-4951). The global 10% tolerance has been the cause of plenty of "why won't it scale?" incidents. Now you can set it per HPA.
  • Storage Version Migrator moves in-tree (KEP-4192). Re-encrypting Secrets or migrating CRD storage versions used to need an extra component that was easy to forget. Having it built in makes those jobs a routine task instead of a project.
  • KYAML (KEP-5295). A stricter, unambiguous YAML subset for Kubernetes output, which avoids problems like "Norway is false". It's a small change, but I've lost real hours to whitespace.
  • DRA, keeps growing. Device taints and tolerations, resource health in Pod status, and a standard numaNode attribute all reached GA. If you run GPUs, Dynamic Resource Allocation is no longer experimental.

Two alpha features also stood out. A Recreate strategy for StatefulSet rollouts (KEP-3541) is something I've been working around for years. Node lifecycle conditions like DrainInProgress and MaintenancePlanned (KEP-5683) could finally give drain tooling a shared language.

My checklist for the next hop

  1. Run the ingress-nginx selector on every cluster, and book in the Gateway API migration.
  2. Check the apiserver_requested_deprecated_apis metric and sort by removed_release.
  3. Find out which kube-proxy mode each cluster runs. If it's IPVS, plan the move now.
  4. Check that every node is on cgroup v2, especially old node images.
  5. Search bootstrap scripts for static Pods that reference Secrets or ConfigMaps.
  6. Upgrade one minor version at a time, and stay within the version skew policy for kubelets.

None of this is glamorous, and that's the point. The best upgrade I ever did was the one nobody noticed, because the prep work happened months earlier.
